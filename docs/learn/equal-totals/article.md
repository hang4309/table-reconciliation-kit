# 两张表合计都是35，为什么还没有对上？

核对库存表时，最容易先看最后一行。两边都是35，很容易让人以为结束了。下面这组六行合成数据里，问题恰恰藏在明细。

|商品键|表A数量|表B数量|逐条结果|
|---|---:|---:|---|
|A|10|10|相同|
|B|20|18|数量不同|
|C|5|没有该键|只在表A|
|D|没有该键|7|只在表B|
|合计|35|35|合计相同并不能证明明细一致|

表A：10+20+5=35。表B：10+18+7=35。商品B少了2，C和D却不是同一个商品。把所有问题压成一个总数，差异就互相掩盖了。

实际操作可以分成三步。第一步保留两份原表，明确什么才是“一条相同的记录”：本例全部在主仓，SKU足够区分；如果同一商品分多个仓位，不能直接照抄单列SKU配对。第二步列出数量差异和单边记录，空键或重复键留给人工处理。第三步根据业务依据确认原因，再决定是否改表。程序找到差异，不等于已经知道哪一边正确。

本页附的浏览器工具可以实际复现这个例子。打开工具，点“载入合成示例”，会得到1条匹配、1条差异、左边和右边各1条独有记录；点“导出差异CSV”，文件中保留了来源行号。

工具比较的是UTF-8 CSV里的文本；`01`与`1`不同，不做金额容差或模糊匹配，也不直接打开XLSX。真实文件先确认编码、键和列映射，不能把这组小样例当作所有表格都已适配的证明。
